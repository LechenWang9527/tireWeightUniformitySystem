## 一、一句话定位

**把「今天全厂质量不好」这句废话，变成「先修 CU621 这台硫化机，因为它 10 月 19 日那次调参改坏了，建议改回某参数」这一条可执行指令。**

系统不是"看数据的看板"，而是一套**质量溯源决策系统**：输入一天的检测数据，输出一份排序好的「待修清单」——修哪台机、为什么、怎么修、影响多少人。

---

## 二、业务背景：四个痛点与四个设计

| 痛点 | 现象 | 对应设计 |
|---|---|---|
| **不知道先看哪台** | 几十台机、几百个规格，每天都有飘的，人力只够查几台 | 双重排序：拖累分（规格级）+ √平滑影响分（机台级） |
| **不知道是不是调参害的** | 质量波动后，工艺员和操作工互相怀疑，没有证据 | CGRS 调参日志 + 受控对比 ΔCPK，给因果证据 |
| **不知道该改成什么** | 知道机台有问题，但不敢乱动参数 | 三套推荐策略（按机型分流） |
| **同一件事反复发生** | 老问题换个规格又出现，经验留不住 | 全量血缘链 + 组合树，把经验固化成规则 |

## 三、系统全景

```
┌────────────────────── 数据源 ──────────────────────┐
│ ① Redshift YOUR_SCHEMA.yield_flat_table（单胎检测数据）│
│ ② CGRS 调参日志（SQL Server，每日导出 parquet）        │
│ ③ Recipes.csv（规格公差 USL/LSL，唯一限值来源）        │
└───────────────────┬────────────────────────────────┘
                    ↓ ETL（拉取 → 清洗 → 原子替换）
        backend/data/*_cleaned.parquet（约 154 万行）
                    ↓ 启动时全量载入
        DuckDB 内存表 clean_yield / cgrs_records
                    ↓ FastAPI 20 个接口
        前端四行漏斗（宏观 → 规格 → 批次 → 单胎）
```

**一句话概括数据流**：三个源汇成一张「单胎档案」，用六个公式算出「谁最该修」，再用四行屏按「宏观→规格→批次→单胎」把人引到那台机台面前。

## 四、数据层

### 4.1 三个数据源

| 源 | 位置 | 内容 | 更新 |
|---|---|---|---|
| **Redshift** | `YOUR_SCHEMA.yield_flat_table`，库 `YOUR-DATAWAREHOUSE`，端口 5439 | 单胎检测明细，主键 `barcode` | 增量拉取 |
| **CGRS** | `YOUR-MES-HOST\YOUR-MES-INSTANCE` / `YOUR_MES_DB` | 工艺参数变更日志 | 外部每日导出 |
| **Recipes.csv** | `backend/data/Recipes.csv` | 规格公差基准 | 静态 |

> **关键架构决策**：系统**不直连 CGRS 数据库**，只读取别人每日导出的 parquet。好处是与外部系统解耦（对方挂了不影响看板），代价是调参数据有 1 天延迟。

### 4.2 单胎档案与血缘

一条 `barcode` 串联全流程，这是所有下钻分析的基础：

```
物料批次 → 胎面/胎圈/内衬/胎侧/帘布/带束层/冠带层 → 成型(GT) → 硫化(CT) → 终检(TU) → 动平衡(TB)
```

共 **13 道工序**：胎面、胎圈、内衬、胎侧、带束层1、带束层2、帘布层1、冠带层1、冠带层2、成型 GT、硫化 CT、终检 TU、动平衡 TB。

**关联规则的差异**（最容易被问到的点）：

- **成型（GT/TB）**：规格绑定紧，按「机台 + 规格 + 时间窗」关联
- **硫化（CT/CU）**：参数跟着模具走，必须**精确匹配机台号**（CU621 就是 CU621；左模 `CUL06` / 右模 `CUG06` 绝不混用）
- **终检（TU）**：无调参，只能横向比较「同规格哪台机器历史最好」

### 4.3 清洗五件事

| 任务 | 规则 | 为什么 |
|---|---|---|
| **量纲统一** | TU 谐波 ×10（daN→N）；TG 几何 ×1000（m→mm） | 源系统单位不统一，不换算 CPK 全错 |
| **班次归日** | `tu_first_loc_timestamp - 8h` → 生产日 | 工业日 08:00 → 次日 08:00 |
| **分期标注** | 三期 P3 / 四期 P4 | **不许跨期比较**，设备与工艺不同代 |
| **限值挂接** | LEFT JOIN `Recipes.csv`，键 `LPAD(TRIM(ART10),10,'0')` | CPK 的唯一依据 |
| **异常标记** | `is_anomaly_tu/tg/tb` + `anomaly_sources` | 一次不良可能同时由多工段导致 |

**占位符过滤**（真实业务里的坑）：源数据用 `960/990/9960/9980/-9980` 等表示"该项不检测"，必须转 NULL；`1050` 要当 `105.0` 处理。**转 NULL 后 = 不考核，绝不用默认值兜底。**

### 4.4 ETL 运行机制

```
fetch_data.py  → 增量拉取（安全水位线 = MAX(tu_first_loc_timestamp) - 1 天；冷启动 31 天）
clean_data.py  → 流式清洗（处理 154 万行不爆内存）
run_pipeline.py→ 编排；先写 .tmp，校验行数后原子 rename 覆盖
scheduler.py   → 默认每 30 分钟触发一次
```

**原子替换的价值**：Web 服务随时可能读文件，直接覆盖会读到半截文件。`tmp + rename` 保证「要么旧完整版，要么新完整版」。

## 五、指标与口径

### 5.1 17 项检测指标 + 1 项物理指标

| 工段 | 指标 | 含义 | 单位 | 换算 | 类型 |
|---|---|---|---|---|---|
| TU | RFPP / RFH1 / RFH2 | 径向力峰峰值 / 一阶 / 二阶谐波 | N | ×10 | 单侧 |
| TU | LFPP / LFH1 | 侧向力峰峰值 / 一阶谐波 | N | ×10 | 单侧 |
| TU | CONY / PLYS | 锥度效应力 / 帘布层效应力 | N | ×1 | **双侧** |
| TG | TBUL / BBUL | 上/下胎侧凸起 | mm | ×1 | 单侧 |
| TG | TDEP / BDEP | 上/下胎侧凹陷 | mm | ×1 | 单侧 |
| TG | TLRO / BLRO / CRRO | 上/下胎侧、胎冠径向跳动 | mm | ×1 | 单侧 |
| TB | TBALW / BBALW / SBALW | 上/下侧动不平衡、静不平衡 | g | ×1 | 单侧 |
| 其他 | 胎重偏差率 | 实际 vs 目标 | % | — | ±2.8%（**不走 CPK**） |

指标字典定义在 `backend/core/cpk.py:INDICATORS_SPEC`，一个指标名可查出「列名、限值列、换算倍率、单/双侧、单位」五件事。

**胎重为什么单独处理**：重量的合格标准是「均值偏差率 ±2.8%」，不是分布宽度，硬套 CPK 会得出误导性结论。

### 5.2 CPK 计算规则

```python
# 单侧（14 项）
CPK = (USL - μ) / (3σ)
# 双侧（CONY / PLYS）
CPK = min((USL - μ)/(3σ), (μ - LSL)/(3σ))
```

| 规则 | 实现 |
|---|---|
| 截断范围 | `[-5, 5]` |
| σ ≤ 1e-6（退化） | 返回 `1.33` |
| USL、LSL 都为空 | 返回 `None`（不考核） |
| 分组粒度 | **指标 × 规格 × 时间窗 × 对象**（不是"一个规格算一次"） |
| 全厂加权 | `Σ(CPKᵢ × Nᵢ) / ΣNᵢ`，单日单规格 N<5 先剔除 |

### 5.3 四条口径红线

1. **公差只来自 `Recipes.csv`**：没配 = 不考核，绝不设默认值
2. **生产日 = 08:00 → 次日 08:00**：所有按天统计必须用 8 小时偏移
3. **不跨工段、不跨分期推荐**：成型只和成型比，三期不与四期混比
4. **不时间穿越**：查历史日期，检索窗固定 `[target_date - 30天, target_date]`

## 七、诊断算法（系统的大脑）

### 7.1 拖累分（StableScore）—— 决定「先看哪个规格」

```
拖累分 = (全厂加权 CPK − 该规格 CPK) × 该规格样本数
```

- **不是**按 CPK 绝对值排序。CPK 0.42 但只有 8 胎的规格，拖累远小于 CPK 0.95 有 5000 胎的规格
- 符号约定：**负值 = 在拉低全厂**
- 排序按绝对值
- **只有同一天内可比**

### 7.2 影响分（Impact）—— 决定「先修哪台机」

```
影响分 = 贡献 × √N_machine / Σ√N_i
```

**为什么开根号**：线性加权会让大产量机台永远背锅。实测 TU8（1300 胎）与 CU621（50 胎）相差 26 倍，开根号后压缩到 5.1 倍，CU621 得以浮到 Rank1 Critical（−0.038），TU8 退到 Rank2（−0.025）。

**两个分数的分工**：拖累分回答「哪个规格在拖后腿」，影响分回答「这个规格里哪台机最该修」。

### 7.3 三级预警瀑布

```
守门（Gate）：Δ% = (今日 − 近3日均值) / 近3日均值
      Δ% > 0（没变差）→ 直接排除，不参与预警
              ↓
🔴 红色：有调参恶化证据（ΔCPK < 0）或 连续 ≥2 天排名第 1
🟠 橙色：Δ% ≤ −35%，或 在榜 ≥3 天但未连续霸榜
🟡 黄色：新上线 / 仅在榜 2 天 / 有负贡献但未达阈值
```

**守门的必要性**：TB254 从 0.735 升到 0.789（+7.4%），虽然数值仍低于 1.33，但**它在变好**，不该报警。没有守门就会天天报假警。

### 7.4 CGRS 受控对比（ΔCPK）

回答「这次变差是不是调参导致的」。

```
按机台拆路径 → 取调参前后各最多 20 胎 → 分别算 CPK → ΔCPK = after − before
```

**四道护栏**（防止小样本骗人）：

| 护栏 | 阈值 | 目的 |
|---|---|---|
| 双侧样本 | 各 ≥ 5 胎 | 样本太少 CPK 无意义 |
| 单侧上限 | ≤ 20 胎 | 调参后工艺会继续漂移，取太多会混入后续变化 |
| 跨天限制 | ≤ 1 天 | 隔太久无法归因 |
| 不平衡比 | max/min ≤ 2.5 | 两侧产量严重失衡则整条路径丢弃 |

外加**同日隔离**：before 与 after 不能跨日历日，否则会被班次口径污染（历史上这个 bug 曾把 before 样本截成 0）。

### 7.5 三套推荐策略

| 工段 | 参数与谁绑定 | 推荐逻辑 |
|---|---|---|
| **成型 GT / TB** | 与规格绑定 | 锁 `spec_prefix7`（前 5 位模糊匹配已废弃）；优先同机台同规格近 30 天，其次同工段同分期兄弟机 |
| **硫化 CT / CU** | 与模具绑定，与规格无关 | 必须精确机台匹配；规格只按后 7 位对齐 |
| **终检 TU** | 不能调参 | 直接推荐同规格历史 CPK 最好的机台（`get_best_tu_machine_for_spec`） |

```python
def _get_top_warning_provider():
    global _top_warning_provider
    if _top_warning_provider is None:
        from backend.services.machine_service import get_top_warning_machines
        _top_warning_provider = get_top_warning_machines
    return _top_warning_provider
```

## 十二、已知问题与技术债

| 问题 | 影响 | 建议 |
|---|---|---|
| **数据停在 2026-10-22** | 演示时看到的是两周前的数据 | 跑一次 `run_pipeline.py --full-fetch` |
| CPK 公式有三份实现（SQL / Python / JS） | 改口径需同步三处，易漂移 | 长期收敛到单一实现或加一致性测试 |
| 8 小时班次偏移硬编码在 SQL 字符串 | 新查询漏减就会口径不一 | 抽出常量/函数 |
| `config.py` 残留个人机器路径 `d:/Ava/...` | 技术债 | 清理 |
| 前端承担部分业务规则（如「排除 Top10」） | 后端报表无法复现 | 下沉到 service |
| `tests/` 目录为空 | 无回归保护 | 至少补 CPK 与预警的单元测试 |
| 本机无外网 | pip/npm 装不了 | 依赖靠本地复制，换机需重建环境 |
| wiki 与实际代码有漂移（如 30 秒 vs 30 分钟） | 误导读代码的人 | 以代码为准，文档标注版本 |

## 十三、术语表

| 术语 | 含义 |
|---|---|
| **CPK** | 过程能力指数，衡量过程输出相对公差的稳定程度 |
| **USL / LSL** | 规格上下限，来自 Recipes.csv |
| **TU / TG / TB** | 均匀性 / 几何尺寸 / 动平衡三个检测工段 |
| **GT / CT** | 成型机 / 硫化机 |
| **CGRS** | 工厂 MES 的工艺参数变更记录系统 |
| **ΔCPK** | 调参前后 CPK 变化量，负值代表调参后变差 |
| **拖累分** | 规格对全厂加权 CPK 的拉低程度 × 产量 |
| **影响分** | 机台对规格的贡献度 × √产量 |
| **守门** | 预警前置条件：没变差（Δ%>0）直接排除 |
| **分期 P3/P4** | 三/四期产线，设备与工艺代际不同，不可混比 |

## 附：一句话收尾

> 这套系统的价值不在于它算得准，而在于**它把"每一步为什么这么算"都写成了可检查的规则**——量纲、班次、限值、样本门槛、护栏、口径统一，全都有明确出处。所以它的数字可以被质疑、被复核、被追责。
