### Step 2 · 数据剥离：先看数据，后看代码（2~3 小时）

这是**整个方法论里性价比最高的一步**。业务系统的复杂度 80% 在数据，代码只是搬运。

**动作**
1. 画血缘链（读 `wiki\02` + `wiki\03`，约 30 分钟）：

```
Redshift  YOUR_SCHEMA.yield_flat_table
   ↓ fetch_data.py        增量拉取（安全水位线 etl_state.json）
yield_flat_table_joined_100.parquet            212 MB
   ↓ clean_data.py        Recipes 匹配限值 / 量纲统一 / 异常物化
yield_flat_table_joined_100_cleaned.parquet    221 MB
   ↓ core/db.py           载入 DuckDB 内存表 clean_yield
API
```

2. 建**字段字典**（不求全，只求关键 20 个）。直接查真数据：

```python
from backend.core.db import qry
rows = qry("SELECT * FROM clean_yield LIMIT 3")
print(list(rows[0].keys()))          # 43 个字段的真实名单
```

重点搞清这几组命名规律（搞清规律就不用背 43 个字段）：

| 命名模式 | 含义 | 例子 |
|---|---|---|
| `*_first` | 终检首条的**测量值** | `rfh1wc_first` |
| `grade_*_first` | 该指标的**评级**（A/a 为合格） | `grade_rfh1wc_first` |
| `standard_*` / `*_usl` / `*_lsl` | 该规格的**公差上下限**（来自 Recipes） | `standard_rfh1` |
| `*_workcenter` | 该工序的**机台号** | `gt_workcenter`、`ct_workcenter` |
| `*_lot` | 该部件的**物料批次** | `second_ply_lot` |
| `is_anomaly_*` / `anomaly_sources` | 清洗阶段**物化**出来的异常标记 | `is_anomaly_tu` |

3. 记住三个"物理常识"（这是领域知识，代码里看不出来）：

- **量纲**：TU 的峰谐波要 **×10** 才是牛（N）；TG 已统一为毫米；TB 是克；
- **班次**：工业生产日是 **08:00 → 次日 08:00**（`tu_first_loc_timestamp - 8 小时`）；
- **机型前缀**：`TB*/GT*` = 成型，`CU*/CT*` = 硫化，`TU*` = 终检；还有**三期/四期**分期，绝不跨期比。

**产出物**：数据字典（20 个字段）+ 一张血缘图。

**验收**：随便说一个指标（比如 CONY），你能立刻答出：它的测量值列、限值列、单位、属于哪个工段、是单侧还是双侧公差。

### Step 3 · 金线穿透：只追一条线，追到 SQL（3~4 小时）

**这是最核心的一步**。整个项目有 20+ 个接口，但**结构是同构的**：追通一条，其余都是变体。

**选线标准**：选一个"每天必看 + 逻辑简单"的，推荐 **`/api/trend/cpk` + `indicator=rfh1`**。

**逐层记录（每层只记三件事：入口、关键变量、出口）**

| 层 | 文件 | 你要找什么 |
|---|---|---|
| ① 用户动作 | `Dashboard.vue`（1869 行，只搜关键字） | 搜 `loadCpkTrend`，看它从哪个组件事件触发 |
| ② 前端请求 | `src\api\index.js`（67 行，全读） | `getCpkTrend` 传了哪些参数 |
| ③ 路由 | `backend\routers\trend.py`（71 行，全读） | 参数默认值、校验 |
| ④ 服务 | `backend\services\trend_service.py`（780 行，只读 `get_trend_cpk`） | SQL 怎么拼、怎么分组 |
| ⑤ 内核 | `backend\core\cpk.py`（118 行，全读） | `INDICATORS_SPEC` 与 `calc_cpk` |
| ⑥ 数据 | `backend\core\db.py`（99 行，全读） | `qry()` 怎么拿到 DuckDB |

**关键技巧：用 `INDICATORS_SPEC` 当索引**

`cpk.py` 里这 18 条字典是全项目的**"指标总表"**，一条记录就串起了五个位置：

```python
"rfh1": {"group": "TU", "label": "RFH1 径向力一次谐波",
         "col": "rfh1wc_first",     # ← SQL 里查哪一列
         "usl_col": "standard_rfh1", # ← 限值从哪来
         "scale": 10.0,              # ← 要不要乘 10
         "unit": "N", "is_double": False}
```

> 以后遇到"某个指标的数不对"，按 `前端 indicator → INDICATORS_SPEC → SQL 列 → scale → calc_cpk` 顺一遍，5 分钟定位。

**产出物**：一张**调用链卡片**（A4 大小），写明：URL、参数、SQL 骨架、返回结构、单位换算、涉及的表。

**验收**：不看代码，能默画出从"点击日期"到"图上出现一条 CPK 曲线"的完整链路；并且能回答"如果我想加一个指标，要改哪 4 个地方"。

### Step 4 · 算法内核：只读 4 个函数（3 小时）

业务系统的价值不在 CRUD，在**这几个算法**。它们都有明确的业务动机，必须连"为什么"一起读。

| 算法 | 位置 | 一句话原理 | 为什么必须懂 |
|---|---|---|---|
| **CPK 统一计算** | `core/cpk.py: calc_cpk` | `min((USL-μ)/3σ, (μ-LSL)/3σ)`，结果截断到 `[-5, 5]`；`σ ≤ 1e-6` 时直接返回 `1.33` | 全站口径的唯一真源，改错一个字全厂数字全错 |
| **产量平方根平滑** | `services/machine_service.py` | `影响分 = 净负偏离 × √产量 / Σ√产量` | 解决"大产量机台背黑锅"，是系统最核心的业务创新 |
| **IQR 异常判定**（旧版） | `111\analyse.py` + `111\data_logic.md` | 按规格分组，`Q1-1.5IQR ~ Q3+1.5IQR` | 理解"异常"的最初定义，便于对照现行 Grade 体系 |
| **CGRS 路径拆分对比** | `services/cgrs_service.py` | 调参前后各取 20 胎，按 GT→CT→TU 路径分组，算 ΔCPK | 全项目最复杂的业务逻辑，含 5 胎门槛与 2.5 倍失衡剔除 |

**读法**：每个函数先读 docstring 和变量名 → 再读公式 → **最后用真数据手算一遍**，和系统输出对比。对不上就说明你没读懂。

**产出物**：每个算法写 5 行"人话解释 + 一个手算例子"。

**验收**：能解释"为什么 1300 胎的机台不该排第一，而 50 胎的应该"，并能举出系统里的实例（`CU621` vs `TU8`）。

## 4. 三个加速技巧

### 技巧一：对比法 —— 用旧版理解新版

`111\` 是**同一个业务的 Streamlit 单体原型**（`analyse.py` 601 行 + `tabs/` 5 个文件）。它和 v2 的关系是"草稿 → 成品"。

**读法**：同一件事看两遍，比如"机台异常定位"：
- `111\tabs\tab2_machine.py`（293 行，Streamlit 直白写法）
- `v2\services\machine_service.py`（1238 行，分层写法）

**你会瞬间明白 v2 为什么要分那么多层**——因为原型里一个 tab 就 300 行，五个 tab 加数据清洗就撑不住生产了。

### 技巧二：决策考古 —— 用 git 和记忆文档读"为什么"

代码只告诉你"是什么"，`MEMORY_SUMMARY.md` 和 commit log 告诉你"为什么"。

```powershell
git log --oneline          # 36 次提交，一天就能扫完
git show <commit> --stat   # 看某次重构动了哪些文件
```

`MEMORY_SUMMARY.md` 里藏着大量**血泪教训**（比如"为什么废除前 5 位模糊匹配"、"为什么 8 点班次必须统一"）。**这些是代码里永远读不出来的**，却是你避免重蹈覆辙的唯一途径。

### 技巧三：反向阅读 —— 从 `/docs` 倒着走

打开 `http://127.0.0.1:8088/docs`，看到的是**运行时的真相**（比源码里的装饰器更可信）。挑一个返回 200 的接口，让 FastAPI 帮你把参数列出来，再反查实现。适合"我只想知道这个数怎么来的"这类窄问题。

## 6. 常见误区（都是踩过的坑）

1. **拿 `docs\wiki\` 当唯一真源** —— 它和 `untitled1\wiki\` 是两份拷贝，已经漂移；有冲突时**以代码为准**。
2. **相信注释里的旧口径** —— 项目经历过"CPK 从 `[0,5]` 改到 `[-5,5]`"的大迁移，旧注释残留过。
3. **在 `main.py` 找业务逻辑** —— 它只有 69 行，业务在 `routers/` + `services/`。
4. **忽视 8 点班次** —— 左右两个图表口径不一致的 bug，历史上出现过不止一次。
5. **以为 `weight`（胎重）也走 CPK** —— 它 100% 保留"均值偏差%"逻辑，是**故意的业务保护**。
6. **改完只看页面** —— 没跑 `npm run build` + `py_compile`，等于没验证。
7. **直接在主分支上改** —— 当前工作区有 15+ 个未提交改动，先 `git status`。
8. **想一次读完** —— 这个项目 1.2 万行代码 + 1.4 万行文档，**追一条线**的效率是通读的 20 倍。

## 9. 最后一句
