## 2. 框架一 · 业务框架（它在替谁做决定）

### 2.1 四个业务痛点（系统的存在理由）

| 痛点 | 系统的解法 | 落在哪块屏 |
|---|---|---|
| 指标太多、口径不一 | 17 项指标统一量纲与公差，全厂加权 CPK | Row 1 |
| 出问题查不到源头 | 打通 物料批次 → 成型 → 硫化 → 终检 的血缘 | Row 2/3 |
| 大机台永远背锅 | √产量 平滑的影响分 | Row 2 右侧 |
| 调参凭经验、不知好坏 | CGRS 调参前后受控对比 ΔCPK | Row 2 行动表 + Row 4 弹窗 |

### 2.2 四行漏斗 = 四个层级的问句

```
Row1 「今天全厂好不好？」        → 宏观，看趋势与异常量
Row2 「哪个规格/哪台机最该修？」  → 定位，看行动表与桑基图
Row3 「是哪批料、哪条胎坏的？」   → 溯源，看批次曲线与单胎散点
Row4 「是不是那次调参搞坏的？」   → 归因，看机台组合与调参对比
```

> 记住这四个问句，比记住组件名有用一百倍。**任何新功能，先问它回答哪个问句。**

## 3. 框架二 · 数据框架（数字凭什么可信）

### 3.1 单胎血缘：一条轮胎的完整档案

`barcode`（唯一主键）串起：13 道工序的机台 → 各部件的物料批次（Lot）→ 17 项质检值 → 17 项 Grade 评级 → 时间戳。

13 道工序固定为：胎面 / 胎圈 / 内衬 / 胎侧 / 带束层1 / 带束层2 / 帘布层1 / 冠带层1 / 冠带层2 / **成型 GT** / **硫化 CT** / **终检 TU** / 动平衡 TB。

> 分析时只看后三道（GT→CT→TU），因为它们是物理变异的主要来源；前 10 道作为"物料批次"维度参与溯源。

### 3.2 四条口径约定（**框架里最容易出错的部分**）

| 约定 | 内容 | 为什么必须记 |
|---|---|---|
| **量纲** | TU 峰谐波 ×10 → 牛(N)；TG 已 ×1000 → 毫米(mm)；TB 克(g)；CONY/PLYS 原本就是 N | 差 10 倍会让 CPK 全错，但界面看起来"很正常" |
| **班次** | 工业日 = 08:00 → 次日 08:00（时间戳减 8 小时派生 `tu_first_shift_date`） | 历史上出现过左右两图对不上的 bug |
| **分期** | `ct_shop` = P3/P4，机台绝不跨期比选 | 跨期比较在物理上无意义 |
| **限值** | USL/LSL 只来自 `Recipes.csv`；占位符（960/990/996/9980…）视为"不考核"置 NULL | 没配就不算 CPK，**绝不给默认值** |

### 3.3 三张表的跨系统映射（最容易讲不清、也最能体现功力）

| | 生产大宽表 | CGRS 变动日志 | CGRS 参数全量 |
|---|---|---|---|
| 机台 | `gt_workcenter` / `ct_workcenter` | `Workcenter` | `Workcenter` |
| 工序 | 13 道字符串列 | `ProcessTypeID`：119=成型一段KM、125=成型二段PU、123=硫化 | 同左 |
| 规格 | `article10`（10 位） | `ProdSpecific2`（辅 1） | `MaterialMasterID` |
| 变化量 | 17 项测量值 | `TechOffsetHistoryValueTo`（生效偏置） | `ParameterValue`（基准） |

**GT 与 CT 的关联规则完全不同，这是框架级差异**：

- **成型 GT**：机台要**派生候选池**（`TB254` ↔ `TB154` 一段/二段配对），规格按 `article10` 或**前 7 位前缀**模糊匹配 `ProdSpecific2`；
- **硫化 CT**：机台**绝对精确匹配**（`CU621` 就是 `CU621`，左模 CUL06 / 右模 CUG06 绝不互相借用），规格按**后 7 位**对齐 `MaterialMasterID`。

> 一句话记：**成型"配对找"，硫化"精确对"**。成型是组装件，分一段/二段；硫化是模具，物理刚性绑定。

## 4. 框架三 · 计算框架（六个公式撑起全部输出）

| # | 名称 | 公式 | 作用 | 位置 |
|---|---|---|---|---|
| 1 | **CPK** | 单侧 `(USL-μ)/3σ`；双侧 `min((USL-μ)/3σ,(μ-LSL)/3σ)`，截断 `[-5,5]`，`σ≤1e-6`→1.33 | 全站唯一口径 | `core/cpk.py` |
| 2 | **加权 CPK** | `Σ(CPKᵢ×Nᵢ)/ΣNᵢ`，先剔除单日单规格 N<5 | 全厂大盘 | `trend_service` |
| 3 | **√产量平滑** | `Impact = Contrib × √Nₘ/Σ√Nᵢ` | 防大机台背锅 | `machine_service` |
| 4 | **拖累分 StableScore** | `(CPK全厂加权 − CPK单规格) × N规格` | 规格排序与红橙黄 | `article_service` |
| 5 | **调参 ΔCPK** | `CPK_after − CPK_before`，同一受控路径、双侧≥5 胎、失衡比≤2.5 | 判断调参好坏 | `cgrs_service` |
| 6 | **三级预警瀑布** | 守门（变化率>0 直接排除）→ 🔴（调参恶化 / 霸榜≥2天）→ 🟠（跌>35% / 连续在榜）→ 🟡（新上线 / 负贡献在榜） | 行动表排序 | `machine_service` |

### 4.1 六个公式的因果链（这才是"框架"）

```
公式1 CPK  ──► 公式2 全厂加权 ──► 公式4 拖累分（规格排序）
   │                                      │
   └──► 公式3 机台影响分（√平滑）──► 公式6 三级预警（谁上榜）
                     │
                     └──► 公式5 调参 ΔCPK（是不是调参害的）
```

**理解要点**：公式 1 是地基，2/3 是两个方向的聚合（规格维度 / 机台维度），4/6 是排序规则，5 是因果验证。**六个公式不是并列的，是一棵树。**

### 5.1 全局状态只有一个源头

Pinia `store/filter.js` 维护全局变量：`cpkIndicator`（17 项之一）、`selectedPhase`（all/p3/p4）、`selectedDate`、`selectedArticle`、`trendGranularity`、`dateRange`。

```
顶栏改指标/期别/日期
      ↓ （写入 Pinia）
Dashboard.vue 的 watch 触发
      ↓ （并发发起）
loadCpkTrend / loadWarningArticles / loadMachineProcessSankey / loadArticleLotCpk
      ↓
整屏联动刷新（趋势图、行动表、桑基图同时换成同一口径）
```

**框架含义**：**所有屏幕共享同一套筛选条件**。这是"改一处、全屏动"的设计，也是历史上口径 bug 的高发区（一旦某个 loader 忘了带参数，两块屏幕就对不上）。

## 6. 框架五 · 工程框架（它是怎么被跑起来的）

### 6.1 六层依赖（只能向下，不能向上）

```
routers（装配参数）→ services（业务编排）→ core（纯函数）→ db（DuckDB）
        ↑___________禁止反向 import___________↓
```

- `core/` 必须是**确定性纯函数**，只进出参；
- 跨 service 调用用**延迟注入钩子**（`_top_warning_provider` 那种），避免循环 import；
- `main.py` 只做装配（69 行），业务都在 services。

### 6.2 两个"时钟"（容易混淆）

| 时钟 | 周期 | 干什么 |
|---|---|---|
| Redshift 增量拉取 | 由 ETL 守护进程触发 | 拉新数据写 parquet |
| ETL 全流程 | **默认 30 分钟**（`scheduler.py --interval 30`） | 拉取 + 清洗 + 原子替换 |
| CGRS 导出 | 每日一次（外部定时任务推送） | 生成 `cgrs_data/*.parquet` |

> ⚠️ **文档说"每 30 秒"，代码是 30 分钟**。这就是"文档漂移"的典型——以代码为准。

### 6.3 部署拓扑

```
本地：npm run build → deploy_to_server.py
        ↓ SMB
服务器 \\YOUR-SERVER-IP\tu ai\TireWeight_Uniformity_Analysis
        ↓ NSSM 守护
FastAPI:8088（异常退出 1 秒自愈） + ETL 定时任务 + 开机自启
```

## 7. 框架六 · 边界框架（它会在哪里骗你）

四条红线反过来读，就是**四个已知失效模式**：

| 红线 | 失效模式 | 研究时怎么验证 |
|---|---|---|
| 不许伪造公差 | 没配限值的规格被**静默排除**，样本悄悄变少 | 查某规格 CPK 为空时，先看 `Recipes.csv` 有没有这一项 |
| 不许跨工段/跨期推荐 | 物理不可比的机台被强行比较 | 看推荐结果的分期标签是否一致 |
| 不许时间穿越 | 用未来数据解释历史（最隐蔽） | 任何"历史日"查询都应有 `[T-30, T]` 窗口 |
| 不许核心层反向依赖 | 循环 import，服务起不来 | 看 `core/` 顶部有没有 import services |

再加三个**业务层**的边界，值得单独记住：

1. **样本门槛**：单日单规格 <5 胎不参与加权；CGRS 双侧各 <5 胎不算 ΔCPK；失衡 >2.5 倍整条剔除。
2. **回看窗口**：历史分析固定回溯 30 天；推荐参数看近 30 天。
3. **`weight`（胎重）不走 CPK**：它是"均值偏差率"，这是**故意的业务保护**，不是 bug。

## 10. 避坑：文档与代码不一致的地方（研究型读者必看）

我核对时发现了几处**文档漂移**，它们本身是最好的教材：

| 文档说法 | 代码事实 | 启示 |
|---|---|---|
| "Redshift 每 30 **秒**增量抽取" | `scheduler.py` 默认 **30 分钟** | 周期类参数一律以代码为准 |
| 全局状态在 `store/filterStore.js` | 实际是 `src/store/filter.js` | 文档里的文件名别照抄 |
| `docs/wiki/` 与 `untitled1/wiki/` 同名文档 | 两份内容已漂移 | 只信一份，且以代码为最终裁决 |
| 早期注释写 CPK 截断 `[0,5]` | 现在是 `[-5,5]` | 大迁移后的旧注释是陷阱 |

**方法**：遇到文档与代码冲突 → **代码为准** → 在笔记里记一条"口径变更"，因为你很可能是下一个人踩坑的。
